# ТЗ: правки юридических страниц arwox.ru по внешней проверке (dcfg-hfkdm)

Основание: `docs/research/2026-10-25-legal-docs-review.md`. Исполнитель — агент Claude Code в этом репозитории.
Источник истины — файлы `landing/site78/<lid>/`. Порядок выкладки и запреты — `AGENTS.md`, раздел «Landing dev/prod».

## Как применять

1. Каждую правку вносить в оба блока страницы: `*.draft.html` и `*.public.html`. HTML-разметку блоков не менять, меняется только текст.
2. После каждой страницы проверять через `grep -c`: новая фраза встречается 1 раз, старая — 0 раз. Вывод проверки вставить в тело PR.
3. «[дата публикации]» агент подставляет сам в день выкладки страницы на prod: дата в формате ДД.ММ.ГГГГ. Других скобок `[…]` в текстах для страниц нет.
4. Выкладка юридических страниц — отдельный атом, через скрипт из ветки `claude/dcfg-hfkdm-deploy`. Сначала dev (сайт 80), проверка, потом prod (сайт 78) — только словом владельца.
5. Одна страница — один коммит. В конце дополнить `docs/research/2026-10-25-legal-docs-gap.md` статусами G1–G29.

Текущие правки PR #71 (G3, G4, G7) сохраняются. Пункт U1 ниже заменяет текст 388 целиком, включая правку G3.

## U12 — резерв форм только в контуре РФ (G8, слово владельца 25.10)

Владелец, 25.10: резервный сервер находится вне РФ. Персональные данные должны оставаться в контуре России. На этом сервере допустима только логика бэкенда, заявки через него идти не должны.

Сейчас при сбое Яндекса сторож `forms-gw-guard.sh` переключает DNS `forms.arwox.ru` на этот сервер (`dns-switch.sh apply outage`), см. `architecture.md`, раздел «Поток заявки (резерв)». Тогда браузер отправляет форму на сервер вне РФ, `server.py` её обрабатывает, а при отказе Битрикс24 кладёт заявку в очередь на диске. Это запись и хранение ПДн граждан РФ вне баз в РФ — 152-ФЗ ст. 18 ч. 5. Кроме того, это трансграничная передача без уведомления — ст. 12 ч. 3.

Что сделать:

1. Резервный путь заявки — готовый механизм `forms-failover/forms-fallback-switch.sh`. При сбое шлюза он заменяет кнопку формы на ссылку на CRM-форму Битрикс24 `https://b24-pne9rr.bitrix24.site/crm_form_yoolu/`. Форму обслуживает ООО «1С-Битрикс», данные остаются в РФ. Сторож при сбое вызывает этот механизм, а не `dns-switch.sh apply outage`.
2. Убрать из сторожа и из `forms-ctl.sh` переключение DNS форм на сервер вне РФ. `dns-switch.sh apply normal` остаётся для возврата на шлюз Яндекса.
3. На сервере вне РФ остаются только сторож, проверки и уведомления, которые не получают ПДн: проверка шлюза, баланс, счётчики без содержимого заявок. Процесс pm2 `forms-backup` заявки больше не принимает.
4. Очередь `/var/lib/forms-backup/spool`: дослать в Битрикс24 то, что в ней есть, сделать бэкап по правилу `AGENTS.md`, затем удалить ПДн с сервера вне РФ. Удалить также бэкап, когда заявки подтверждены в Битрикс24.
5. CRM-форма `crm_form_yoolu`: проверить, что согласие в ней ведёт на текст 388 (новая редакция из U1) и даётся отметкой, без предустановленной галочки.
6. Инвариант в `AGENTS.md` «отказ Bitrix24 → очередь резерва» переписать: при отказе Битрикс24 заявка не теряется и хранится только в контуре РФ. Где именно — решает агент после проверки того, что делает `index.py` при отказе Битрикс24 в Cloud Function.
7. В юридических текстах не указывать адрес сервера, его хостинг и страну. В U1 п. 5 и U2 п. 6 сервер не упоминается.

Порядок: сначала `forms-test.arwox.ru` (`forms-ctl.sh test`), проверка. На `forms.arwox.ru` — только словом владельца, как требует `AGENTS.md`. Правка `forms-failover/*` — это runtime: угрозы и откат описать в атоме до правки.

Проверки:

- `grep -n "apply outage" forms-failover/forms-gw-guard.sh forms-failover/forms-ctl.sh` → 0 вызовов;
- на тесте при остановленном шлюзе кнопка формы ведёт на `crm_form_yoolu`, а `dig forms-test.arwox.ru` показывает CNAME Яндекса;
- `ls /var/lib/forms-backup/spool` на сервере вне РФ пуст.
